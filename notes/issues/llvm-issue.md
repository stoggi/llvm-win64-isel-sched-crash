While compiling a Rust program, I encountered a crash in LLVM on a Linux host while cross compiling for a Windows target (`x86_64-pc-windows-msvc`) where the same code compiled successfully for a Linux target (`x86_64-unknown-linux-gnu`). I have used Claude Code (Opus 5.5) to help me reproduce and understand this crash. I have clearly marked sections that were generated by the LLM with ⚠️ where the explanation may be incorrect or beyond my understanding.

I have put together the examples below in this repo: [stoggi/llvm-win64-isel-sched-crash](https://github.com/stoggi/llvm-win64-isel-sched-crash)

## Summary

When preparing the scheduled instructions for Windows vs Linux, LLVM passes function arguments differently, with registers and/or the stack, because the two targets use different calling conventions. As a result, the unit scheduler can exercise different paths depending on the target's calling convention. In a strange and specific set of circumstances, the Windows target used registers and the stack to pass variables to a function, where the Linux target just used registers. This, combined with a call to `sin()` on a float32 (which LLVM turns into a call to the `sinf` library function), created two scheduling conflicts that couldn't be resolved by reordering. The flags must cross the call-frame setup, and the sinf libcall waits on the open call sequence. As a result, its last-resort path picks the call-sequence conflict first, and treats the CallResource pseudo-register as a real register. The register lookup then goes out of range, which segfaults on LLVM 22, and fails with `LLVM ERROR: SmallVector unable to grow` in LLVM 23 (and on main).

> ⚠️ Claude Code summary:
> `llc` crashes in X86 instruction selection, in the bottom-up list scheduler (`ScheduleDAGRRList`), on a block where a Win64 call passes an `i1` on the stack and an `llvm.sin.f32` result in a register. The scheduler reaches the last-resort path of `PickNodeToScheduleBottomUp` with the first pending interference being on the special call-sequence resource (`TRI->getNumRegs()`), and passes it to `getMinimalPhysRegClass` as if it were a register. With assertions, `Reg < ArrayRef(Mapping).size()` fails. Without assertions it does not stop there and fails later: `LLVM ERROR: SmallVector unable to grow` (main, 23.1.4) or a SIGSEGV (22.1.2).

## Steps to Reproduce

Here is a minimal rust code example, compiled as a library `lib.rs`, created from the real game code that initially triggered the crash:

```rust
unsafe extern "C" {
    fn callee(a: *const u8, b: *const u8, c: *const u8, x: f32, flag: bool);
}

pub fn repro(p: &u64, c: bool, x: f32, y: f32, a: *const u8, b: *const u8, d: *const u8) {
    let flag = *p != 0;
    let sel = if c { 0.8 } else { x };
    let sum = y.sin() + sel;
    unsafe { callee(a, b, d, sum, flag) };
}
```

The important pieces to set up the conditions for the crash are:

1. The flag boolean is a result of comparing a value loaded from memory.
2. A select with the if statement.
3. Calling `sin()` on a float, added to the result of the select.
4. Passing all these to a function with the win64 ABI, with the flag as the fifth parameter such that it gets passed on the stack instead of a register.

Compile for release, this works on `x86_64-unknown-linux-gnu`:
```
$ cargo build --release
```

But it crashes with `x86_64-pc-windows-msvc`:
```
$ cargo build --release --target x86_64-pc-windows-msvc
```

### Identifying the crashing component

On the unreduced bitcode:
- `opt -O3 repro.bc -disable-output` succeeds, so it is not an optimizer crash.
- `llc repro.bc`, `llc repro.bc -relocation-model=pic` and `llc repro.bc -relocation-model=static` all crash, so it is a code generator crash. The same three commands also crash on `repro.reduced.ll`.

### What it does not crash on

Each of these compiles `repro.reduced.ll` (or its variant) without error:

- The same IR with an `x86_64-unknown-linux-gnu` triple (System V convention, all arguments in registers).
- `llc -pre-RA-sched=fast`, which is also a workaround.
- `llc -O0`.
- An explicit `call float @sinf(...)` in place of `@llvm.sin.f32`.

## Root Cause

> ⚠️ Claude Code summary:
> An assertions build of `llc` from main stops with `getMinimalPhysRegClass(...): Assertion 'Reg < ArrayRef(Mapping).size()' failed`, and `-debug-only=pre-RA-sched` shows why:
>
> 1. The compare producing the `bool` folds the load of `*p`, so it is chained *before* the outer call's `ADJCALLSTACKDOWN64`. Its `EFLAGS` are read by the `SETCCm` that stores the `bool` into the stack argument slot, which is *after* `ADJCALLSTACKDOWN64`. That pseudo clobbers `EFLAGS`, so as built, the flags would have to live across a node that destroys them. Only the scheduler's last-resort path (duplicate or unfold the compare, or copy `EFLAGS`) can fix that.
> 2. The `sinf` libcall from `llvm.sin.f32` is chained only to the entry token, so its call sequence is ready while the outer one is open and waits on the scheduler's pseudo-register for call sequences, `CallResource`.
> 3. With both stuck, the last-resort path in `PickNodeToScheduleBottomUp` takes the *first* pending node, which is the libcall's, and treats `CallResource` (`TRI->getNumRegs()`, one past the last real register) as a physical register. The register-class lookup is out of range: an assertion with assertions on, a garbage register class and a null read (LLVM 22) or a runaway list (LLVM 23) without.
>
> The patch below makes that path skip call-resource interferences and resolve the real `EFLAGS` one; LLVM then splits the compare's load back out, as the `fast` scheduler also does (though it places the load after the `sinf` call). With the patch, `check-llvm-codegen-x86` still passes (5745 passed, 15 expectedly failed, 2 unsupported), builds of main with and without assertions compile the reproducer and the larger function it was reduced from, and the patch's new regression test fails without the change.

> ⚠️ Claude Code explanation of the fix and the alternatives:
>
> **How the patch fixes it.** When nothing in the available queue can be scheduled and backtracking does not help, `PickNodeToScheduleBottomUp` falls back to its last resort. The blocked nodes are in `Interferences`, each with the live registers that block it in `LRegsMap`. The last resort takes the first entry, assumes it is blocked by one physical register, and looks up that register's class with `getMinimalPhysRegClass` and its cross-copy class. It then works on the node that defines the register (`LRDef`): if the value cannot be copied directly, `CopyAndMoveSuccessors` tries to unfold a folded load (`TryUnfoldSU`) and otherwise duplicates the node; failing that, it inserts copies. All of this needs a real register. `CallResource` is a pseudo-register numbered `TRI->getNumRegs()` that the scheduler uses to stop call sequences from nesting, and a node blocked on it is unblocked by scheduling the call sequence that holds it, not by copying anything. The patch picks the first interference whose blockers do not include `CallResource`. Here that is the `SETCCm` blocked on `EFLAGS`, whose defining node is the `CMP64mi32`. `CopyAndMoveSuccessors` unfolds it into a separate `MOV64rm` load and a register compare (`-debug-only=pre-RA-sched` prints `Unfolding SU(15)`). The compare no longer carries the load's chain dependency, so it can be scheduled inside the call sequence and the `EFLAGS` live range no longer has to cross `ADJCALLSTACKDOWN64`. With the outer call sequence then schedulable, the `sinf` call sequence's wait on `CallResource` clears in the ordinary way. If every interference is on `CallResource`, nothing in this path could resolve it, so the patch reports a fatal error instead of indexing past the end of the register tables.
>
> **Other ways it could be addressed.** None of these have been tried.
>
> 1. *Sort instead of search.* Order `Interferences` so that nodes blocked only on real registers come first. This is the same fix written differently, but it would also change which real-register interference is chosen when there are several, which the patch deliberately leaves alone.
> 2. *Avoid the `EFLAGS` conflict at instruction selection.* Do not fold a load into a compare whose flags are consumed after an `ADJCALLSTACKDOWN64` the compare is chained before. This removes this trigger at the source, but the scheduler would keep the latent bug for any other pattern that reaches the last resort with a `CallResource` interference first.
> 3. *Make `ADJCALLSTACKDOWN64` not clobber `EFLAGS`.* It declares `EFLAGS` as clobbered because it can be expanded into a `SUB` of `RSP`. `X86FrameLowering::BuildStackAdjustment` can already use `LEA` instead when the flags are live into the block, but dropping the clobber would need that guaranteed wherever the pseudo expands into an adjustment. It touches every x86 call, and again only removes this trigger.
> 4. *Serialise the expanded libcall.* The `sinf` call that legalisation creates from `llvm.sin.f32` is chained to the entry node, which is what lets it become ready while the outer call sequence is open. Chaining it ahead of the outer call sequence would avoid the second conflict, but the scheduler is meant to handle independent call sequences through `CallResource`, and that would constrain scheduling for every expanded libcall.
> 5. *Work around it without changing LLVM.* `llc -pre-RA-sched=fast` compiles the test case, as does changing the shape of the call. In the original Rust code, passing the arguments to the callee by reference in a struct, so the `bool` is no longer a stack argument, avoided the crash.
>
> The patch is the narrowest of these. When the first interference is on a real register, `find_if` returns it and the path runs exactly as before. Behaviour only changes when the first interference is on `CallResource`, which today reads past the end of the register tables.
