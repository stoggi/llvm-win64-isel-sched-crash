While compiling a Rust program, I encountered a crash in the LLVM on a Linux host while cross compiling for a Windows target (`x86_64-pc-windows-msvc`) where the same code compiled successfully for a Linux target (`x86_64-unknown-linux-gnu`). I have used Claude Code (Opus 5.5) to help me reproduce and understand this crash. I have clearly marked sections that were generated by the LLM with ⚠️ where the explanation may be incorrect or beyond my understanding.

I have put together the examples below in this repo: stoggi/llvm-win64-isel-sched-crash

## Summary

When preparing the scheduled instructions for Windows vs Linux, the LLVM can choose to pass function variables differently with registers and or the stack. As a result, the unit scheduler can exercise different paths depending on the target architecture. In a strange and specific set of circumstances, the Windows target used registers and the stack to pass variables to a function, where the Linux target just used registers. This, combined with an unusual call to `sin()` on a float32, created a scheduling conflict that couldn't be resolved by reordering. The flags must cross the call-frame setup, and the sinf libcall waits on the open call sequence. As a result, it's last-resort path picks the call-sequence conflict first, and treats the CallResource pseudo-register as a real register. The register lookup then fails, which on LLVM 22 this segfaults, and loops until running out of memory in LLVM 23 (and on main).

> :warning: Claude Code Summary:
> `llc` crashes in X86 instruction selection, in the bottom-up list scheduler (`ScheduleDAGRRList`), on a block where a Win64 call passes an `i1` on the stack and an `llvm.sin.f32` result in a register. The scheduler reaches the last-resort path of `PickNodeToScheduleBottomUp` with the first pending interference being on the special call-sequence resource (`TRI->getNumRegs()`), and passes it to `getMinimalPhysRegClass` as if it were a register. With assertions `Reg < ArrayRef(Mapping).size()' failed. Without assertions it does not stop there and fails later: `LLVM ERROR: SmallVector unable to grow` (main, 23.1.4) or a SIGSEGV (22.1.2).

```rust
unsafe extern "C" {
    fn callee(a: *const u8, b: *const u8, c: *const u8, x: f32, flag: bool);
}

pub fn repro(p: &u64, c: bool, x: f32, y: f32, a: *const u8, b: *const u8, d: *const u8) {
    let flag = *p != 0;
    let sel = if c { 0.8 } else { x };
    let sum = y.sin() + sel;

```

The important pieces to setup the conditions for the crash are:

1. The flag boolean is a result of a comparing a value loaded from memory.
2. A select with the if statement.
3. Calling `sin()` on a float, added to the result of the select.
4. Passing all these to a win64 ABI, with the flag as the last parameter such that it gets passed on the stack instead of a register.

## Root Cause

> :warning: Claude Code Summary:
> An assertions build of `llc` from main stops with `getMinimalPhysRegClass(...): Assertion 'Reg < ArrayRef(Mapping).size()'  failed`, and `-debug-only=pre-RA-sched` shows why:
> 
> 1. The compare producing the `bool` folds the load of `*p`, so it is chained *before* the outer call's `ADJCALLSTACKDOWN64`. Its `EFLAGS` are  read by the `SETCCm` that stores the `bool` into the stack argument slot, which is *after* `ADJCALLSTACKDOWN64`. That pseudo clobbers `EFLAGS`, so as built, the flags would have to live across a node that destroys them. Only the scheduler's last-resort path (duplicate or unfold the compare, or copy `EFLAGS`) can fix that.
> 2. The `sinf` libcall from `llvm.sin.f32` is chained only to the entry token, so its call sequence is ready while the outer one is open and waits on the scheduler's pseudo-register for call sequences, `CallResource`.
> 3. With both stuck, the last-resort path in `PickNodeToScheduleBottomUp` takes the *first* pending node, which is the libcall's, and treats `CallResource` (`TRI->getNumRegs()`, one past the last real register) as a physical register. The register-class lookup is out of range: an assertion with assertions on, a garbage register class and a null read (LLVM 22) or a runaway list (LLVM 23) without.
> 
> `llvm/fix-scheduledagrrlist.patch` makes that path skip call-resource interferences and resolve the real `EFLAGS` one; LLVM then splits the compare's load back out, as the `fast` scheduler also does (though it places the load after the `sinf` call). With the patch, LLVM's 5762 X86 code generation tests still pass, a release build of main compiles the reproducer and the game's original function (unpatched, it fails with `SmallVector unable to grow`), and the patch's new regression test fails without the change. The sections below are the investigation that led there.
